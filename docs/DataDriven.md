# Infinitesia — архитектура и план перехода на Data-Driven систему

## 1. Общая концепция

Infinitesia — масштабная симуляционная игра, объединяющая идеи Dwarf Fortress, GregTech и комплексных симуляторов естественных и социальных систем.

В проекте планируется моделировать:

- Космос: звёзды, планетные системы, орбиты, формирование планет.
- Планетологию: строение планет, геологию, географию, климат и гидрологию.
- Физику и химию: вещества, элементы, соединения, агрегатные состояния, реакции, энергию.
- Природные ресурсы: минералы, руды, жидкости, газы, органические материалы.
- Производство: добычу, обработку сырья, промышленное оборудование, производственные цепочки.
- Биологию: организмы, виды, популяции, экосистемы, эволюцию.
- Общество: разумных существ, поселения, государства, политические системы, идеологии.
- Экономику: товары, торговлю, рынки, производство, распределение ресурсов.
- Технологии: исследования, научные открытия, технологические эпохи.
- Космическую деятельность: ракеты, космические станции, колонии и освоение других планет.

Основной принцип проекта — **Data-Driven Architecture**. Игровые определения, характеристики объектов, производственные процессы, материалы, виды существ, технологии и другие элементы игрового мира описываются в XML-файлах.

C++ отвечает за общие механизмы симуляции, обработку данных, алгоритмы и исполнение игровых систем. XML содержит определения конкретного игрового контента.

Такая структура позволит расширять игру через добавление XML-контента и развитие универсальных систем обработки данных.

## 2. Текущее состояние репозитория

В репозитории `MikoMikocchi/Infinitesia` уже сформирована основа нескольких важных подсистем.

По текущей структуре проекта:

| Подсистема | Существующая реализация                            |
| ---------- | -------------------------------------------------- |
| Foundation | Базовые механизмы, время, координаты               |
| Chemistry  | Состав веществ, химические формулы, молярная масса |
| Planetary  | Конвейер генерации планет                          |
| Materials  | `MaterialDef`, `MaterialCatalog`                   |
| Geology    | Геологические модели и провинции                   |
| Blocks     | Формы блоков и их свойства                         |
| World      | `VoxelWorld`, чанки, `TerrainSource`               |
| Simulation | Фиксированный шаг симуляции, планировщик           |
| Gameplay   | `EntityStore`, `GameWorld`, предметы, `WorkSystem` |
| Content    | JSON-каталоги и реестры                            |
| Tools      | `tools/check_dependencies.py`                      |

Также в проекте уже присутствуют полезные архитектурные решения:

- `PlanetPipeline` организует генерацию планеты через отдельные стадии.
- Стадии генерации описывают необходимые входные данные через `needs` и создаваемые результаты через `provides`.
- `SimulationRuntime` предоставляет основу для управления симуляцией.
- `VoxelWorld` и система чанков образуют основу пространственного представления мира.
- Химические и геологические модели уже содержат полезную предметную логику.

Эти подсистемы можно постепенно встроить в новую архитектуру.

### Области для переработки

**Материалы.** Текущий `MaterialDef` объединяет физические свойства материала с характеристиками блоков. Например, `BlockClass`, `digClass`, `walkable`, `diggable`, `opacity` и `emission` относятся к разным уровням описания объекта.

Рекомендуется разделить определения:

- `MaterialDefinition` — химические, физические и механические характеристики материала.
- `BlockDefinition` — свойства блока в игровом мире.
- `ItemDefinition` — характеристики предмета.
- `FormDefinition` — форма и способ представления материала или объекта.

**Сущности.** Текущий `EntityStore` хранит `std::vector<WorldObject>` и выполняет поиск объектов линейным проходом. Для масштабной симуляции рекомендуется миграция на ECS с использованием EnTT.

**Загрузка контента.** Текущие JSON-каталоги и реестры следует постепенно перевести на единую XML-систему загрузки определений.

**Симуляция.** `SimulationRuntime` и существующий планировщик можно сохранить и интегрировать с новой ECS-архитектурой.

## 3. Общая архитектура

Архитектура разделяется на несколько основных уровней.

### 3.1. Core Layer

Фундаментальные типы и механизмы, используемые всем проектом:

- Strong IDs.
- Математика.
- Единицы измерения.
- Время.
- Координаты.
- Геометрия.
- События.
- Утилиты.
- Базовые интерфейсы.

Core должен иметь минимальное количество зависимостей.

### 3.2. Definition Layer

Система игровых определений, загружаемых из XML.

Она отвечает за:

- Чтение XML-файлов.
- Разбор XML-структуры.
- Создание типизированных определений.
- Регистрацию определений.
- Разрешение ссылок между определениями.
- Проверку корректности данных.
- Предоставление доступа к загруженному контенту.

Примеры определений:

- `MaterialDefinition`
- `ElementDefinition`
- `CompoundDefinition`
- `SpeciesDefinition`
- `CreatureDefinition`
- `ItemDefinition`
- `BlockDefinition`
- `MachineDefinition`
- `ProcessDefinition`
- `RecipeDefinition`
- `TechnologyDefinition`
- `BuildingDefinition`
- `BiomeDefinition`
- `PlanetTypeDefinition`

Каждый тип получает собственную C++-структуру с соответствующими полями.

### 3.3. ECS Layer

Система хранения динамических игровых объектов и их компонентов.

Для реализации рекомендуется использовать **EnTT**.

ECS отвечает за:

- Создание и уничтожение сущностей.
- Хранение компонентов.
- Поиск сущностей по компонентам.
- Выполнение систем над группами сущностей.
- Обработку событий.
- Управление динамическим состоянием объектов.

### 3.4. Simulation Layer

Общий исполнитель симуляции.

Включает:

- `SimulationRuntime`
- `SimulationScheduler`
- `SimulationContext`
- `SimulationWorld`
- управление временными шагами;
- порядок выполнения систем;
- обработку событий;
- управление подсистемами симуляции.

### 3.5. Domain Layer

Предметные подсистемы, реализующие физику, химию, геологию, биологию, промышленность и остальные игровые области.

Каждая подсистема должна иметь собственные модели, алгоритмы и системы обработки данных.

### 3.6. Gameplay Layer

Взаимодействие игрока с симуляцией:

- Управление персонажами.
- Предметы и инвентари.
- Добыча.
- Строительство.
- Работа.
- Взаимодействие с объектами.
- Управление поселениями.
- Игровые задания.

### 3.7. Presentation Layer

Отображение состояния игрового мира:

- Рендеринг.
- Интерфейс.
- Камера.
- Ввод.
- Визуализация объектов.
- Отображение информации симуляции.

Отдельные определения желательно хранить в самостоятельных файлах. Каталоги могут содержать индексные XML-файлы, перечисляющие подключаемый контент.

Например:

```xml
<?xml version="1.0" encoding="UTF-8"?>

<catalog>
    <include file="metals/iron.xml"/>
    <include file="metals/copper.xml"/>
    <include file="metals/aluminium.xml"/>
</catalog>
```

Загрузчик должен поддерживать относительные пути, проверку существования файлов, защиту от циклических подключений и детерминированный порядок загрузки.

### 4.2. Идентификаторы определений

Каждое определение получает уникальный ID.

Примеры:

```text
material.iron
material.steel
element.iron
compound.water
species.human
machine.blast_furnace
process.iron_smelting
technology.metallurgy
```

В C++ рекомендуется использовать типизированные Strong IDs:

```cpp
struct MaterialDefinitionId
{
    std::string value;
};

struct SpeciesDefinitionId
{
    std::string value;
};

struct MachineDefinitionId
{
    std::string value;
};
```

Это упрощает проверку ссылок и снижает вероятность передачи идентификатора неподходящего типа.

### 4.3. Пример XML-определения материала

```xml
<?xml version="1.0" encoding="UTF-8"?>

<material id="material.iron">
    <name>Iron</name>
    <description>Pure iron material.</description>

    <composition>
        <element id="element.iron" amount="1"/>
    </composition>

    <physical>
        <density unit="kg/m3">7874</density>
        <melting_point unit="K">1811</melting_point>
        <boiling_point unit="K">3134</boiling_point>
    </physical>

    <mechanical>
        <hardness>4</hardness>
        <elastic_modulus unit="GPa">211</elastic_modulus>
    </mechanical>

    <thermal>
        <specific_heat unit="J/(kg*K)">449</specific_heat>
        <thermal_conductivity unit="W/(m*K)">80</thermal_conductivity>
    </thermal>
</material>
```

В C++ это загружается в типизированную структуру:

```cpp
struct MaterialDefinition
{
    MaterialDefinitionId id;

    std::string name;
    std::string description;

    ChemicalComposition composition;

    PhysicalProperties physical;
    MechanicalProperties mechanical;
    ThermalProperties thermal;
};
```

Числа, единицы измерения и ссылки на другие определения должны проходить проверку при загрузке.

### 4.4. Пример определения машины

```xml
<machine id="machine.blast_furnace">
```

### 4.5. Пример производственного процесса

```xml
<process id="process.iron_smelting">
    <name>Iron Smelting</name>

    <inputs>
        <item id="item.hematite" amount="2"/>
```

Это позволит описывать производственные цепочки данными и обрабатывать их универсальными системами промышленности.

### 4.6. Устройство XML-загрузчика

Рекомендуемый порядок обработки контента:

1. **Discovery** — поиск XML-файлов и каталогов.
2. **Parsing** — разбор XML в промежуточные структуры.
3. **Registration** — регистрация определений в типизированных реестрах.
4. **Reference Resolution** — разрешение ссылок по ID.
5. **Validation** — проверка полей, типов, ограничений и зависимостей.
6. **Finalization** — подготовка неизменяемых реестров для симуляции.

При ошибках загрузчик должен предоставлять понятные сообщения с именем файла, строкой и контекстом ошибки.

Примеры ошибок:

```text
Unknown material reference: material.unobtainium
File: data/industry/recipes/steel.xml
Line: 18

Duplicate definition ID: material.iron
File: data/materials/metals/iron_copy.xml
Line: 3

Invalid unit: kg/second
File: data/materials/metals/iron.xml
Line: 14
```

### 4.7. Реестры определений

Для каждого типа определений создаётся отдельный типизированный реестр:

```cpp
template<typename Id, typename Definition>
class DefinitionRegistry
{
public:
    const Definition* find(const Id& id) const;
    bool contains(const Id& id) const;

    void registerDefinition(Definition definition);

private:
    std::unordered_map<
        std::string,
        Definition
    > definitions_;
};
```

Примеры конкретных реестров:

```cpp
using MaterialRegistry =
    DefinitionRegistry<MaterialDefinitionId, MaterialDefinition>;

using SpeciesRegistry =
    DefinitionRegistry<SpeciesDefinitionId, SpeciesDefinition>;

using MachineRegistry =
    DefinitionRegistry<MachineDefinitionId, MachineDefinition>;
```

Общий `ContentManager` может объединять доступ ко всем реестрам.

После успешной загрузки и проверки определения становятся неизменяемыми на протяжении обычного игрового сеанса. Это обеспечивает стабильность ссылок и упрощает работу систем симуляции.

### 4.8. XML-библиотека и проверка схем

Для C++20-проекта можно рассмотреть:

- **pugixml** — разбор и работа с XML, удобный для производительного загрузчика.
- **tinyxml2** — компактный XML-парсер с простым API.
- **XSD** — формальная проверка структуры XML-документов.

Для первой реализации достаточно выбрать один XML-парсер и создать собственный слой загрузки определений. Проверку XML-структуры можно постепенно усилить XSD-схемами и дополнительной семантической валидацией.

## 5. ECS и EnTT

Для динамических игровых объектов рекомендуется использовать EnTT.

EnTT предоставляет:

- Registry.
- Entity.
- Component storage.
- Views.
- Groups.
- Signals.
- Совместную работу с пользовательскими системами.

### 5.1. Применение ECS

ECS хорошо подходит для:

- Людей.
- Животных.
- Мобильных существ.
- Предметов.
- Машин.
- Транспорта.
- Строительных объектов.
- Других динамических игровых объектов.

Для плотных пространственных данных удобно использовать специализированные структуры:

- Воксели хранятся в массивах чанков.
- Геологические слои используют специализированные модели.
- Планетные системы используют доменные структуры.
- Состояния государств и крупных экономических систем могут храниться в предметных моделях.

Выбор структуры определяется характером данных и способом их обработки.

### 5.2. Компоненты ECS

Пример базовых компонентов:

```cpp
struct TransformComponent
{
    Vec3 position;
    Quaternion rotation;
};

struct SpeciesComponent
{
    SpeciesDefinitionId species;
};

struct HealthComponent
{
    float current;
    float maximum;
};

struct NeedsComponent
{
    float hunger;
    float thirst;
    float sleep;
};

struct InventoryComponent
{
    std::vector<ItemStack> items;
};

struct BehaviorComponent
{
    BehaviorState state;
};
```

Для машин:

```cpp
struct MachineComponent
{
    MachineDefinitionId definition;
};

struct EnergyComponent
{
    float storedEnergy;
    float maximumEnergy;
};

struct MachineInventoryComponent
{
    std::vector<ItemStack> inputs;
    std::vector<ItemStack> outputs;
};

struct MachineProcessComponent
{
    ProcessDefinitionId activeProcess;
    float progress;
};
```

Компоненты содержат текущее состояние конкретной сущности. Постоянные характеристики сущности загружаются из Definition Layer по ID.

### 5.3. Системы ECS

Системы обрабатывают компоненты через запросы EnTT.

Например:

```cpp
class MovementSystem
{
public:
    void update(entt::registry& registry, float deltaTime)
    {
        auto view = registry.view<
            TransformComponent,
            VelocityComponent
        >();

        for (auto entity : view)
        {
            auto& transform =
                view.get<TransformComponent>(entity);

            const auto& velocity =
                view.get<VelocityComponent>(entity);

            transform.position +=
                velocity.value * deltaTime;
        }
    }
};
```

Предметные алгоритмы должны использовать доменные типы и интерфейсы. ECS обеспечивает доступ к игровым объектам и их состоянию.

## 6. Разделение материалов, предметов и блоков

Для материалов и объектов рекомендуется создать несколько независимых типов определений.

### MaterialDefinition

Содержит свойства самого вещества:

- Химический состав.
- Плотность.
- Твёрдость.
- Прочность.
- Теплопроводность.
- Электропроводность.
- Температуру плавления.
- Температуру кипения.
- Теплоёмкость.
- Другие физические и химические свойства.

### FormDefinition

Описывает форму и физическое состояние материала:

- Твёрдый блок.
- Порошок.
- Гранулы.
- Жидкость.
- Газ.
- Волокно.
- Лист.
- Пруток.

### ItemDefinition

Описывает конкретный игровой предмет:

- ID.
- Название.
- Форму.
- Материал.
- Массу.
- Объём.
- Размер.
- Свойства инвентаря.
- Возможные способы использования.

### BlockDefinition

Описывает объект в воксельном мире:

- Геометрическую форму.
- Проходимость.
- Прозрачность.
- Разрушаемость.
- Класс добычи.
- Светоизлучение.
- Взаимодействие с окружающими блоками.

Эта структура позволяет одному материалу использоваться во множестве форм и предметов.

Например, железо может существовать в виде руды, слитка, порошка, листа, прута и конструкционного блока. Все эти варианты ссылаются на общие характеристики материала.

## 7. Организация систем симуляции

Системы симуляции желательно распределить по предметным областям.

### 7.1. Физика

## 10. Интеграция EnTT с CMake

Для подключения EnTT в проекте с CMake можно использовать FetchContent.

Пример:

```cmake
include(FetchContent)

FetchContent_Declare(
    EnTT
    GIT_REPOSITORY https://github.com/skypjack/entt.git
    GIT_TAG master
)

FetchContent_MakeAvailable(EnTT)
```

После подключения библиотеку можно добавить в зависимости нужной цели:

```cmake
target_link_libraries(
    Infinitesia
    PRIVATE
        EnTT::EnTT
)
```

Для воспроизводимых сборок следует закрепить конкретный стабильный тег или commit EnTT после выбора версии.

ECS-слой проекта должен предоставлять собственный интерфейс для игровых систем. Это позволит держать зависимости от EnTT в пределах инфраструктуры ECS.

## 12. Первый вертикальный прототип

Для проверки архитектуры рекомендуется сделать небольшой законченный производственный цикл.

### XML-контент

Создать определения:

- `element.iron`
- `material.iron`
- `material.steel`
- `item.hematite`
- `item.iron_ingot`
- `item.steel_ingot`
- `species.human`
- `machine.blast_furnace`
- `process.iron_smelting`
- `process.steelmaking`

### Игровой сценарий

1. XML-загрузчик читает определения.
2. Content Registry регистрирует материалы, предметы, виды существ, машины и процессы.
3. Создаётся игровой мир.
4. Через ECS создаётся персонаж.
5. Персонаж получает задачу добычи гематита.
6. Добытые предметы поступают в инвентарь.
7. Персонаж переносит сырьё к доменной печи.
8. Машина выполняет процесс плавки.
9. В результате появляется железо.
10. Следующий процесс позволяет получить сталь.
11. Сталь используется для изготовления детали.
12. Деталь применяется при создании другого объекта или машины.

### Критерии готовности

- Все перечисленные определения загружаются из XML.
- Ссылки между определениями корректно разрешаются.
- Ошибки в XML дают понятные сообщения.
- Персонажи, предметы и машины представлены через ECS.
- Производственные процессы используют общие системы.
- Добавление нового материала или рецепта выполняется через XML.
- Для нового материала или рецепта не требуется отдельная специальная ветка C++-логики.

Этот прототип проверит совместную работу XML, реестров, EnTT, систем симуляции, предметов и промышленности.

## 13. Что важно заложить в фундамент

### Типизированные определения

Каждая предметная сущность получает собственную структуру и реестр. Общие механизмы загрузки и регистрации позволяют работать с ними единообразно.

### Стабильные идентификаторы

Определения связываются через ID. Компоненты ECS и предметные модели используют эти ID для доступа к соответствующему контенту.

### Централизованная загрузка XML

Единый загрузочный конвейер управляет обнаружением файлов, парсингом, регистрацией, разрешением ссылок и валидацией.

### Единицы измерения

Для физических величин следует создать общую систему единиц. Она должна поддерживать преобразование значений, проверку совместимости единиц и хранение физических величин в согласованном внутреннем представлении.

### Разделение определений и текущего состояния

XML описывает свойства вида объекта, материала, машины или процесса. Текущие значения здоровья, температуры, запаса энергии, состояния производства и других параметров хранятся в динамическом состоянии мира.

### Расширяемые предметные системы

Каждая область получает собственные определения и алгоритмы. Общий Content Layer обеспечивает загрузку и связывание данных между областями.

### Диагностика контента

Для XML-контента нужны понятные ошибки, предупреждения, отчёты о неиспользуемых определениях и проверка ссылок.

### Автоматические тесты

В проекте должны быть тесты загрузчика, реестров, ECS, симуляции и предметных алгоритмов.

## Итоговая цель

Infinitesia должна получить архитектуру, в которой:

- C++ реализует универсальные механизмы и алгоритмы симуляции.
- XML определяет игровой контент и характеристики объектов.
- Definition Layer предоставляет типизированные неизменяемые определения.
- EnTT управляет динамическими игровыми сущностями.
- Simulation Layer организует выполнение систем.
- Domain Layer реализует физические, химические, биологические, геологические, промышленные и социальные процессы.
- Gameplay Layer связывает симуляцию с действиями игрока.
- Presentation Layer отображает состояние мира.

В результате новые материалы, существа, машины, технологии, рецепты, минералы и другие игровые элементы можно будет добавлять через XML, используя уже существующие механизмы симуляции.

Архитектура должна поддерживать постепенное расширение мира от отдельных материалов и производственных процессов до целых планет, экосистем, цивилизаций и межзвёздных колоний.
