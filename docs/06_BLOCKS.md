# Блоки: материалы, формы и свет

Дизайн-документ (задача 10, этап 1), версия 3. Код не меняется. После утверждения документ
становится описанием модели блока и света, а реализация идёт по частям (раздел 8).

Что изменилось относительно версии 2: **материал и форма разделены** (как в Dwarf Fortress).
Реестр хранит материалы (из чего сделано) и формы (что построено: сейчас только полный блок, позже
стена, пол, лестница). Клетка хранит пару `{material, shape}`. Версия 2 добавила единый реестр с
тегами, текстуры только в `assets/` и раздел про свет; версия 1 была про переход с `BlockType`.

## 0. Принятые решения

| Решение | Источник |
|---|---|
| Один реестр со всеми материалами игры, не только геологическими | вы |
| Материал и форма разделены: из материала можно делать блок, стену, пол и т. д. | вы |
| Форма хранится в клетке (`{material, shape}`), одна форма и один материал на клетку; объекты поверх клетки отдельная тема | вы |
| Реализуется только форма `Full`; остальные формы отдельной задачей, но формат клетки сразу рассчитан на них | вы |
| Все текстуры и цвета в `assets/`; в коде ни цвета, ни имени текстуры | вы |
| Только английские имена блоков, локализации пока нет | вы |
| Море `fluid.seawater`; `water` и `seawater` пока одно и то же по свойствам | вы |
| Свет переделывается: тёмные блоки там, где они не должны быть, это баг модели | вы, гипотеза подтверждена |
| Будут источники света: магма, светильники, блоки | вы |
| Блочный свет цветной (RGB по 4 бита), небесный скалярный | вы |
| Стекло бывает цветным: `opacity` задаётся по каналам RGB | вы |
| Лёд слегка гасит свет (`opacity 3`); `built.glass` (стекло, `opacity 0`) добавляется в первую партию материалов | вы |
| Сглаживание света по вершинам включено сразу | вы |
| На время миграции вода остаётся «твёрдой» для работ и путей (как сейчас) | по умолчанию, поправьте |
| Цвета и текстуры земли и песка берутся из каталога, внешний вид изменится | по умолчанию, поправьте |

## 1. Что есть сейчас

### 1.1. Блоки

```cpp
enum class BlockType { Air, Grass, Dirt, Stone, Sand, Water };
struct Block { GridCell cell; BlockType type; MaterialId material = kUnspecifiedMaterial; };
```

Два источника правды: `type` (шесть значений, на нём все правила) и `material` (точный id из
каталога, выдаётся только камню). Каталог (`materials.json` 21 запись + `rocks.json`) уже хранит
`BlockClass`, `digClass`, `density`, `color`, текстуры по ключам; из почв и жидкостей
игра не использует ничего, `digClass` не читает никто.

| Правило | Где | Сейчас |
|---|---|---|
| «Пусто» | `WorkPathfinding`, `WorkOrders` (x2), `WorkMovement`, `WorkExecution`, `WorldInteractionController`, `TerrainMeshBuilder` (x3), `TerrainMeshGeometry` | `type == Air` |
| Можно ли копать, ходить | `WorkOrders`, `WorkPathfinding` | не `Air` (вода тоже) |
| Проходит ли свет | `VoxelWorld::HasSkyAccess` | `Air` и `Water` |
| Стартовая клетка | `StartingCells` | не `Air` и не `Water` |
| Цвет | `GetBlockColor`, `BlockDiagram` | `switch` на 5 цветов в коде; материал учтён только у `Rock` |
| Текстура | `GetFaceLook` | материал по ключу, иначе `block.*` по `type` |
| Допустимость | `SetBlockType` | белый список из 6 значений |

Вода как твёрдое сейчас поведение, а не баг: по ней строят путь и её копают.

### 1.2. Свет

Как работает сегодня:

- `VoxelWorld::HasSkyAccess(cell)` идёт по столбцу вверх до верха сетки; любой блок кроме воздуха
  и воды даёт «нет неба». Для незагруженных чанков каждую клетку спрашивает у `TerrainSource`.
  Стоимость O(высота) на клетку, вызывается на каждую клетку при каждой пересборке меша.
- `TerrainMeshBuilder` при «нет неба» ставит `tint = BLACK` на верхнюю и боковые грани блока
  (строки 132 и 189). Это единственный учёт света в мире.
- Шейдер `world_lighting.fs` освещает только направленным светом от нормали (константы 0.48 +
  0.42·diffuse + 0.12·skyFill). Положения источников и значения света в нём нет.
- Для воздуха в плоскости разреза рисуется верх первого твёрдого блока под ним, затемнённый по
  глубине (`kFloorShadePerLevel`); лампы и «глубина» это отдельный приём, не свет.

Почему блоки бывают тёмными без причины:

1. **Свет только вертикальный.** Блок под выступом, у входа в пещеру, в траншее шириной в один
   блок и т. п. получает полный `BLACK`, хотя рядом открытое небо. Хоть какое-то освещение сбоку
   невозможно, это бит, а не величина.
2. **Всё или ничего.** Два состояния вместо плавного спада; граница между «светло» и «чёрное»
   проходит по сетке блоков.
3. **Одна оценка на блок для всех граней.** Верх и бока красятся одним флагом, хотя боковая грань
   смотрит в соседнюю клетку, у которой свой свет.
4. **Незагруженные чанки.** Результат зависит от того, что загружено, а что запрошено у источника;
   логика размазана между `VoxelWorld` и мешером.
5. **Нет источников.** Магма, светильники, светящиеся блоки не могут ничего осветить.

## 2. Что мы берём у Minecraft и Dwarf Fortress

- **Minecraft:** реестр блоков со строковыми id и свойствами, заданными при регистрации; теги
  (`#water`, `#mineable/pickaxe`), чтобы код не знал конкретных блоков; внешний вид из ресурсов;
  два канала света 0–15 (небо и блок), распространяемых поиском в ширину и обновляемых локально.
- **Dwarf Fortress:** материал отдельно от формы (гранитная стена, гранитный пол, гранитная
  лестница); жидкость отдельным слоем с уровнем; материалы в текстовых данных. Берём разделение
  материала и формы (раздел 3) и мысль, что **уровень жидкости, когда он появится, отдельное
  поле клетки**, а не новый материал на каждый уровень.

## 3. Единый реестр: материалы и формы

Клетка мира описывается двумя числами:

```cpp
using ShapeId = std::uint8_t;
inline constexpr ShapeId kShapeFull = 0;                  // единственная форма на первом этапе

struct BlockState { MaterialId material; ShapeId shape; };   // что лежит в клетке
struct Block      { GridCell cell; BlockState state; };      // type исчезает
```

- **Материал** (`MaterialId`) отвечает, из чего сделано: плотность, твёрдость, цвет, текстура,
  `opacity`, `emission`, теги. Воздух это материал 0.
- **Форма** (`ShapeId`) отвечает, что построено из материала: полный блок, потом стена, пол,
  лестница, рампа. Свойства формы: какие стороны клетки она закрывает (`faceMask`), можно ли по
  ней ходить, пропускает ли она свет сверх материала.
- «Гранитная стена» это `{rock.granite, Wall}`, «деревянный пол» `{planks, Floor}`. Новый материал
  работает во всех формах без правок кода, новая форма во всех материалах.

Все решения про свет, проходимость и копание считаются от пары `(material, shape)`: материал даёт
физику, форма геометрию. Пока существует только `Full`, поведение определяется материалом, как
раньше определяло `BlockType`.

Ограничение выбора «форма в клетке»: клетка хранит один материал и одну форму. Пол и стена из
разных материалов в одной клетке невозможны; такая «композитная» клетка либо получит отдельную
форму (`FloorAndWall`), либо потребует объекта поверх клетки (`EntityStore`). Это решается, когда
появятся сами формы; формат клетки (`BlockState` с запасом) от этого не меняется.

### 3.1. Что в реестре материалов

Реестр содержит **каждый материал**, а не только геологический:

| Диапазон `numericId` | Что | Откуда |
|---|---|---|
| 0-31 | воздух и жидкости (вода, морская вода, рассол, нефть, магма) | `materials.json` |
| 32-511 | породы | `rocks.json` |
| 512-1023 | рыхлый грунт, почвы, лёд | `materials.json` |
| **1024-4095 (новое)** | **прочие материалы**: строительные (доска, кирпич, стекло), светящиеся, руды, и всё, что придумает геймплей | **`assets/blocks/built_materials.json` (новое)** |
| 4096+ | зарезервировано | |

`numericId` стабильны и не переиспользуются (правило каталога сохраняется). `MaterialId` остаётся
`uint16_t`.

Геология остаётся владельцем **своих** данных (породы, минералы, колонки провинций,
`GeologyCatalog`), но «из чего может быть клетка» решает реестр. Он собирается при старте из
`GeologyCatalog` (воздух, жидкости, породы, почвы), `built_materials.json` и `shapes.json` (формы).
Дубликат ключа или id это ошибка загрузки с понятным текстом.

### 3.2. Запись материала

Единая запись `MaterialDef` (расширение существующей, поля геологии не теряются):

| Поле | Тип | Дефолт | Назначение |
|---|---|---|---|
| `key` | строка | обязательно | `rock.granite`, `soil.turf`, `fluid.seawater`, `built.glowstone` |
| `numericId`, `name` | | | как сейчас; только английское имя, без локализации |
| `class` | `Air/Fluid/Loose/Rock/Ice/**Built**` | | **добавляется `Built`** для строительных и прочих |
| `tags` | список строк | по классу | `water`, `fluid`, `soil`, `stone`, `light_source`... |
| `occupied` | bool | `class != Air` | есть ли в клетке вещество (воздух нет) |
| `walkable`, `diggable` | bool | `occupied`; для `diggable` на финальной стадии кроме жидкостей | пути, работы; форма может сузить |
| `opacity` | 0..15 или `[r, g, b]` | см. 3.3 | насколько материал гасит свет, проходящий сквозь него; число = одинаково по каналам, тройка = цветное стекло (красное стекло гасит G и B сильнее R) |
| `emission` | `[r, g, b]`, каждый 0..15 | `[0,0,0]` | цветной свет, который испускает материал; магма `[14, 6, 1]`, белая лампа `[15, 15, 15]` |
| `digClass` | 0..5 | есть | копание |
| `density`, `color` | | есть | цвет только запасной, когда нет текстуры |
| `faces` | `{top, side, bottom}` | `{key, key, key}` | ключи тайлов, см. 3.5 |

### 3.2a. Запись формы

`assets/blocks/shapes.json`, числовой id стабилен (0 = `Full`):

| Поле | Тип | `Full` | Назначение |
|---|---|---|---|
| `key`, `numericId` | | `shape.full`, 0 | |
| `faceMask` | 6 бит | все | какие стороны клетки закрыты целиком: соседние грани скрываются, свет не проходит |
| `walkable` | bool | да | можно ли стоять на форме / ходить |
| `passesLight` | bool | нет | пропускает ли форма свет сверх материала (решётка, пол); для `Full` непрозрачность определяет только `opacity` материала |
| `mesh` | ключ шаблона | `cube` | как строится геометрия; в данных пока только `cube` |

`occupied`, `walkable`, `diggable`, `opacity` клетки: свойство материала, сужаемое формой
(`walkable = material.walkable && shape.walkable`, `opacity` форма может обнулить через
`passesLight`). Для `Full` результат равен свойству материала.

### 3.3. Дефолты свойств по классу

| Класс | `occupied` | `opacity` | примечание |
|---|---|---|---|
| `Air` | нет | 0 | |
| `Fluid` | да | 2 (магма 15, как твёрдая) | вода слегка гасит свет |
| `Loose` | да | 15 | |
| `Rock` | да | 15 | |
| `Ice` | да | 3 | свет проходит, слегка гасится (решено) |
| `Built` | да | 15 | переопределяется данными; `built.glass` (стекло) `opacity 0`, прозрачное; цветные варианты (`built.glass_red` и т. д.) с тройкой `opacity` |

`emission` не выводится из класса: магма и светящиеся материалы задают цвет сами. Стекло входит в
первую партию `built_materials.json` вместе с `built.planks`, `built.brick` и одним светящимся
материалом для проверки света.

### 3.4. Теги

Код не спрашивает «это вода?» по id, а спрашивает тег материала:

```cpp
// Engine-level tags resolved once from names at load; an unknown name is a load error.
enum class Tag { Water, Fluid, Soil, Stone, LightSource, ... };
bool BlockRegistry::Has(MaterialId, Tag) const;
```

`fluid.water` и `fluid.seawater` оба `["water", "fluid"]`, свойства (плотность, цвет, `opacity`)
в данных **идентичны**, пока это решено «одним и тем же». Генерация использует `seawater` для
моря; правила и свет теги не различают.

Теги нужны, чтобы новые материалы подключались данными: «любой `tag: stone` копается киркой»,
«любой `tag: water` можно пить».

### 3.5. Текстуры и цвета только в `assets/`

- Текстуры лежат в `assets/textures/blocks/` по ключу материала: `<key>.png`; для граней
  `<key>_top.png`, `<key>_side.png`, `<key>_bottom.png`. Поиск: грань → `<key>_<грань>` →
  `<key>` → однотонный тайл цвета из реестра. Форма текстур не меняет: стена и пол из гранита берут
  тайлы гранита, геометрию задаёт форма.
- Прежние `block.*` в коде и ассетах исчезают: `block.grass_top/side` переезжают в
  `soil.turf_top.png / soil.turf_side.png`, остальные `block.*` удаляются (у земли, песка и воды
  уже есть `soil.*`, `fluid.*`).
- В коде не остаётся цветов блоков. `GetBlockColor(BlockType)`, `BlockDiagram::BlockColor` и
  похожие `switch` удаляются; цвет всегда из реестра.
- `tools/GenerateBlockTextures.py` генерирует текстуры из реестра по ключам, чтобы список файлов
  не расходился с данными. Тест: у каждого материала реестра есть тайл или цвет.

### 3.6. Где живёт

Новый модуль **`blocks`** (материалы и формы) между `geology` и `world`:
`foundation < chemistry, planet < geology < blocks < world < gameplay < presentation < app`.
Он зависит от `geology` (читает каталог, ему принадлежат `built_materials.json`, `shapes.json` и теги) и ничего не знает
об атласе и графике. `tools/check_dependencies.py` (`MODULE_OF`, `ALLOWED`) и `CMakeLists.txt`
(`infinitesia_add_module`) дополняются.

```cpp
class BlockRegistry
{
public:
    static BlockRegistry Build(const GeologyCatalog&, const std::filesystem::path& assetsBlocks);
    static BlockRegistry BuiltIn();                       // минимум для тестов, без файлов
    const MaterialDef* FindMaterial(std::string_view key) const;
    const MaterialDef* GetMaterial(MaterialId) const;     // nullptr для неизвестного id
    ShapeId FindShape(std::string_view key) const;
    // Горячие запросы: плотные массивы по MaterialId и ShapeId, без строк и хешей.
    bool Occupied(BlockState) const;  bool Walkable(BlockState) const;
    bool Diggable(BlockState) const;  std::uint8_t Opacity(BlockState) const;
    std::uint8_t Emission(MaterialId) const;  bool Has(MaterialId, Tag) const;
    std::uint8_t FaceMask(ShapeId) const;
};
```

Таблица материалов до 4096 записей по 4 байта (16 КБ) и таблица форм до 256 записей; неизвестный
`MaterialId` считается воздухом и логируется один раз, неизвестная форма `Full`. `Block` остаётся
в 16 байт (клетка 12 + материал 2 + форма 1 + выравнивание), а не 20, как сейчас.

## 4. Почвы, вода, камень

Выбор материала по `SurfaceKind` переезжает с `switch` по enum на структуру, разрешаемую из реестра
**один раз** (форма везде `Full`):

```cpp
struct SurfaceMaterials { MaterialId turf, subsoil, sand, bedrock, seawater; };
static SurfaceMaterials SurfaceMaterials::Resolve(const BlockRegistry&);   // по ключам материалов
```

Нет ключа: загрузка падает с понятным сообщением (как сейчас для воздуха и воды).

| Было | Станет | Заметки |
|---|---|---|
| `Grass` (поверхность) | **новый** `soil.turf` (дёрн), `Loose`, `digClass 1` | грани `soil.turf_top/side`, низ `soil.subsoil` |
| `Dirt` (под травой и как поверхность) | `soil.subsoil` (513) | |
| `Sand` | `soil.sand` (516) | |
| `Stone` | порода из геологии; без геологии `rock.bedrock` | `bedrock`: порода-заглушка, `digClass 4`, серый, пустой `modal` |
| `Water` | `fluid.seawater` (2) | `water` и `seawater` одинаковы |

`soil.turf` это «внешний вид поверхности», а `soil.humus` профиль почвы; материал с гранями для травы
отдельный, физика каталога не ломается.

`water` и `seawater` в данных выравниваются (одинаковые плотность, цвет, `opacity`, теги), текстуры
`fluid.water.png` и `fluid.seawater.png` пока совпадают визуально.

## 5. Источники ландшафта

`TerrainSource` сейчас имеет `BlockAt → BlockType` и `MaterialAt → MaterialId`. Остаётся одна
функция, и реестр обязателен:

```cpp
virtual BlockState StateAt(GridCell) const = 0;      // {material, shape}; shape = Full для всей геологии
virtual const BlockRegistry& Registry() const = 0;
```

- `PlanetTerrainSource`: воздух или `seawater` над поверхностью, дёрн или почва сверху, порода из
  геологии ниже; без геологии `bedrock`.
- `NoiseTerrainSource` и тестовые источники (`LocalGameTests`) берут `BlockRegistry::BuiltIn()`.
  Тест на согласованность: `BuiltIn()` совпадает с файлами по ключам и свойствам.
- `VoxelWorld::SetBlockType(cell, BlockType)` → `SetBlock(cell, BlockState)`; проверка «в реестре
  нет такого материала или формы» заменяет белый список из шести значений.
- Форма `Full` единственная, которую выдают генераторы; другие формы появляются только
  постройкой игрока, поэтому `TerrainSource` их не знает.

## 6. Свет

### 6.1. Модель

Два канала по Minecraft, значения 0..15 на каждый блок мира:

Эффективный `opacity` клетки берётся от пары `(material, shape)` (раздел 3.2a): форма,
пропускающая свет (`passesLight`), пропускает его независимо от материала.

- **Небесный свет** (`sky`): полный (15) на открытом небе, идёт вниз без потерь сквозь блоки с
  `opacity 0` и теряет `opacity` в блоке с большим значением; в стороны и вверх 1 единица за шаг
  плюс `opacity` блока. Так возникает полутень у входа в пещеру и под выступом.
- **Блочный свет** (`block`) **цветной**: три независимых канала R, G, B по 0..15. Излучают
  материалы с `emission != [0,0,0]` (магма, светящиеся блоки) и **объекты** (светильники и другое);
  каждый канал на шаге от источника теряет 1 плюс `opacity` блока на пути. Свет двух источников в
  клетке складывается покомпонентным `max`, как в Minecraft для одного канала.
- Небесный свет скалярный и белый; цвет неба и заката появится множителем `daylight` позже
  (вопрос 6).

Яркость клетки по каналу = `max(sky · daylight, block_c)` для c в R, G, B, где `daylight` 0..1
зависит от времени суток и пока 1. Клетка с эффективным `opacity 15` не пропускает свет, но **сам освещается снаружи** (грань смотрит в
соседнюю клетку, см. 6.4).

Распространение: поиск в ширину очередями по правилам Minecraft (добавить свет, убрать свет с
перераспределением соседей), 6 соседей, значения только целые 0..15. Цветной блочный свет это
три независимых прохода по одной и той же очереди (канал обрабатывается, пока его значение в
клетке больше нуля), поэтому стоимость до 3× только там, где есть источники; небо один проход.

### 6.2. Хранение и слой

Модуль `world` (зависит от `blocks`): `LightField` на мир, данные на чанк рядом с блоками:

```cpp
struct WorldChunk { ...; std::vector<std::uint16_t> light; };  // sky 4 бита + block R, G, B по 4 бита
```

Ровно 16 бит на блок: 2 байта на клетку, 8 КБ на чанк 16³ сверх блоков.

`LightField` не знает ни о мешах, ни о графике: `SkyAt(cell)`, `BlockLightAt(cell) → RGB`,
`OnBlockChanged(cell, oldState, newState)`, `AddEmitter(cell, rgb)`, `RemoveEmitter(cell)`.

### 6.3. Когда считается

1. **Генерация чанка:** небесный свет столбцами сверху вниз (15 до первого непрозрачного блока),
   затем поиск в ширину из «граничных» клеток вбок; блочный свет из всех излучающих блоков чанка.
2. **Граница чанков:** для клеток незагруженных соседей берётся блок из `TerrainSource`
   (свет для них не хранится); когда сосед генерируется, граничные клетки пересеваются и свет
   доходит дальше. Свет чанка не считается «окончательным», пока не загружены 4 боковых соседа;
   меш чанка не строится или строится с низким приоритетом (вопрос 5).
3. **Изменение блока** (`SetBlock`): локальные очереди добавления/удаления света вокруг
   клетки; затронутые чанки получают новую `lightRevision`, мешер перестраивает только их.
4. **Объекты-источники:** `EntityStore` вызывает `AddEmitter/RemoveEmitter` при появлении, движении
   и удалении светильников (граница слоя: `gameplay` знает о `world`, не наоборот).

### 6.4. Отрисовка

- Грань блока освещается по свету в **клетке, в которую она смотрит**: верх по клетке сверху, бок
  по соседней клетке. Это убирает «чёрную грань под открытым небом».
- Свет передаётся в шейдер **атрибутами вершины**: RGB блочного света и отдельный канал неба
  (нормированные 0..1), а не заменой текстуры чёрным. Способ передачи четырёх значений (цвет
  вершины плюс второй набор текстурных координат или аналог в raylib) уточняется на шаге L2.
  Шейдер: `light = max(vec3(sky * daylight), blockRgb)`, затем направленный диффуз, как сейчас,
  поверх. Минимальный свет (`ambient floor`) конфигурируется, по
  умолчанию 0.04, чтобы неосвещённое не было чистым нулём.
- **Сглаживание света включено** (решено): значение вершины это среднее света четырёх клеток,
  которые касаются вершины с освещаемой стороны (сама клетка наружу и три соседние), непрозрачные
  клетки в среднее не входят. Работает по всем пяти каналам.
- `BLACK` в мешере и `HasSkyAccess` удаляются. Затемнение «по глубине» от плоскости разреза
  (`kFloorShadePerLevel`) остаётся как отдельный визуальный приём, не свет. Свет считается по
  реальному миру, а не по разрезу: блок у плоскости освещён так, как если бы верхний слой был на месте.

### 6.5. Тесты света

Золотые сценарии на маленьких сетках:

- чистое поле, небо 15, под крышей в один блок рядом с открытым краем 14, 13...;
- вход в пещеру: уровни убывают на 1 за шаг, дальше нуля нет;
- шахта в один блок: на дне 15 по вертикали, сбоку спад;
- установка и удаление блока обновляют свет, как будто свет считался с нуля (сравнение
  инкрементального и полного пересчёта на случайных изменениях);
- магма и светящиеся блоки светят своим цветом и убывают по 1 за шаг на канал, гасятся непрозрачными;
- два источника разных цветов в соседних клетках дают покомпонентный `max`;
- стекло пропускает небесный и блочный свет без потерь сверх шага, лёд гасит на 3 за блок;
- сглаживание: вершина у границы тени получает среднее света, а не ступеньку;
- вода гасит небесный свет медленнее камня.

## 8. Миграция без остановки игры

Принцип: каждый шаг оставляет сборку и `ctest` зелёными, поведение (в том числе вода как
твёрдое) неизменным, кроме явно помеченных. Переходный слой держит оба представления до шага G.

### Линия блоков

| Шаг | Что | Видимое |
|---|---|---|
| **A. Реестр и данные** | модуль `blocks`, `BlockRegistry` (материалы и формы), теги, `built_materials.json`, `shapes.json` (`Full`), `materials.json` v2, `soil.turf`, `bedrock`, `water = seawater` по свойствам; `BuiltIn()`; тесты | нет |
| **B. Правила** | `VoxelWorld::Registry()`; переходная `StateOf(BlockType, MaterialId)` → `BlockState` (известный `material`, иначе по `type`: Grass→turf, Dirt→subsoil, Sand→sand, Stone→bedrock, Water→seawater, Air→air; форма везде `Full`) | нет |
| **C. Потребители** | `work/*`, `StartingCells`, `WorldInteractionController`, `TerrainMeshBuilder` переходят на реестр, по одному файлу | нет |

| **E. Источники** | `PlanetTerrainSource` и `NoiseTerrainSource` выдают материалы; `BlockAt` остаётся обёрткой | нет |

| **G. Уборка** | удалить `BlockType`, `Block::type`, `StateOf`, `SetBlockType`, `kUnspecifiedMaterial`, `block.*` | нет |

### Линия света (после B; независима от C-G)

| Шаг | Что | Видимое |
|---|---|---|
| **L1. LightField** | расчёт неба и блочного света для генерируемых чанков, хранение, тесты 6.5; **ни один потребитель не подключён** | нет |
| **L2. Отрисовка** | мешер читает свет вместо `HasSkyAccess`; шейдер с вершинным светом; сглаживание по вершинам; удалить `BLACK` | да, свет |

## 9. Как проверять

- Перед E зафиксировать тестом «эффективный материал каждого блока» для нескольких планет и позиций;
  B-D его не меняют, E меняет только `Stone` без геологии на `bedrock`.
- Тест воды: путь и копание по воде работают как раньше (C-F).
- Свет: тесты 6.5; визуальная проверка на сценах «выступ», «вход в пещеру», «шахта» до и после L2.
- На каждом шаге: `ctest`, `python tools/check_dependencies.py`, ноль предупреждений.

## 10. Открытые вопросы

1. **Внешний вид земли и песка** по умолчанию из каталога (цвета изменятся). Подгонять под
   прежние? Рекомендация: нет.
2. **Вода как твёрдое.** Сохранить на миграции и решить отдельной задачей (плавание, мосты)?
   Рекомендация: да.
3. **Небо через цветное стекло.** Блочный свет красится стеклом по каналам (решено). Небесный
   свет скалярный, поэтому его гасит минимум из трёх каналов и он стекло не красит. Красить ли небо
   тоже (пятый и шестой канал или цветное небо), решаем вместе с вопросом 4.
4. **Цвет неба.** Когда появится смена суток, цвет и яркость неба идут из планетарной модели
   через `daylight`; пока белый.
5. **Границы чанков.** Строить меш только когда загружены боковые соседи (задержка на краю
   загруженной области) или принять временное «серое» на границах и пересчитать позже?
   Рекомендация: пересчёт позже, меш строится сразу.
6. **Смена суток.** `daylight` пока константа 1; когда планета получит день/ночь, он идёт от
   планетарной модели. Закладываем только параметр в шейдер.
7. **Производительность цветного света.** Три канала дороже одного; измерить на L1-L3. Если
   перестроение чанков окажется медленным, запасной вариант: считать блочный свет скалярным с цветом
   ближайшего источника (хранение 16 бит это позволяет).
8. **Объекты-светильники.** Свет объекта привязан к клетке (дискретно), как блок, или плавно?
   Рекомендация: к клетке, плавного нет.
9. **Сохранения.** В коде формата сохранения мира нет (проверить перед G). Клетка в сохранении это
   пара `numericId` материала и формы, не ключи.
10. **Композитные клетки.** Когда появятся стены и полы: отдельные формы вроде `FloorAndWall` или
    постройки объектами поверх клетки (`EntityStore`)? Решается задачей про формы; формат клетки
    не меняется.
11. **Воздух и форма.** Для воздуха форма игнорируется (хранится `Full`), клетка пуста по классу
    материала. Альтернатива, отдельная форма `Empty`, отвергнута как лишняя.
